落地型 AI Agent 实战：私有知识库接入、RAG 融合与企业权限管控

企业做 AI Agent，真正的难点通常不在模型本身，而在三件事：私有知识能不能稳定接进来，RAG 能不能把检索结果融成可靠答案，权限能不能贯穿到每一次检索和工具调用。三者任何一环失守，Agent 都很难从演示走向生产。

一、私有知识库接入：先治理数据，再谈智能

私有知识库接入不是把文档批量丢进向量库，而是建立一条可维护的数据管线。第一步做数据源盘点：文档、Wiki、工单、邮件、数据库、网盘和业务系统各自更新频率、格式和责任人不同，要按“高价值、高频更新、强权限”分级接入。第二步做解析与清洗：PDF 表格、扫描件、多级标题、附件和脚注容易丢结构，解析后要保留标题层级、章节路径、表格语义和来源链接。第三步做切分与元数据：切分不能只按字数，要按语义段落和标题边界切，给每个片段打上来源、部门、密级、生效时间、版本和可访问范围等元数据。没有元数据的知识片段，后续既难检索也难控权。第四步做增量同步和失效管理：文档更新要能触发重新解析，旧版本要标记失效，避免 Agent 引用过期制度。接入阶段还要设“知识准入”规则，明确哪些内容可入库、哪些只可摘要、哪些必须脱敏。

二、RAG 融合：让检索结果变成可引用答案

RAG 的实战重点不是“有没有向量检索”，而是融合质量。查询侧要做改写和意图识别，把口语问题转成适合检索的关键词与过滤条件；检索侧建议混合检索，向量召回语义相近内容，关键词召回制度编号、产品名和专有名词，再按元数据过滤；排序侧引入重排模型，把真正回答问题的片段往前放。上下文组装要控制长度和多样性，避免同一文档的重复片段挤占空间。生成侧必须要求引用来源，并设置“不知道”机制：检索置信度低、来源冲突或权限不足时，Agent 应明确拒答或转人工，而不是编造。Agent 与 RAG 的结合点在于工具调用：先检索知识，再决定是否调用业务系统查询状态、提交工单或计算数据，每次调用都要带权限上下文。最后建立评估闭环，用真实问题集持续测召回率、引用准确率、拒答合理性和端到端任务完成率，按失败案例回流到解析、切分和排序环节。

三、企业权限管控：检索前过滤，全程可审计

企业权限管控不能靠“生成后删敏感内容”，而要把权限前移到检索和工具调用之前。身份侧统一接入企业 SSO，识别用户、部门、角色和租户；知识侧把文档密级、部门归属、项目范围和字段级权限写入元数据；检索侧在召回阶段就按用户权限过滤，确保无权内容不进入上下文。对高敏字段还要做脱敏和最小披露，Agent 只返回完成任务所需信息。工具调用同样要控权：查询员工数据、提交审批、发送邮件等动作要按角色授权，敏感操作增加二次确认和人工审批。全链路要留审计日志，记录谁在什么时间问了什么、检索了哪些片段、调用了什么工具、返回了什么结果，便于追责和优化。多租户场景还要隔离索引、缓存和日志，防止跨租户泄漏。

落地型 Agent 的心法是：知识接入解决“有没有料”，RAG 融合解决“答得准不准”，权限管控解决“能不能看、能不能做”。三者咬合，Agent 才真正可用、可控、可审计。
